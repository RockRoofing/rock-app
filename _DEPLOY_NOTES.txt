WHAT THIS PACKAGE FIXES
-----------------------
Thirteen environment variables decided who an email came from, what it replied
to, and what address the links inside it pointed at. An environment variable has
ONE value for the whole deployment, so every customer would have sent mail as
Rock Roofing with links into Rock's portal.

Worse than embarrassing. A variation instruction or RAMS approval link is a
token in a URL. Send another company's customer a link on Rock's domain and the
token resolves against Rock's tenant.

There are 60 of these fallbacks across 42 files. This is the first 8 - the ones
that actually send to customers and subcontractors.


THE RULE
--------
When a customer IS in scope, their own setting is used. If they have not got
one, it THROWS.

It does NOT fall back to Rock's value. That is the opposite of how the code read
before, where a missing setting quietly became notifications@rockroofing.co.uk.

A failed notification is a support call. A notification sent from the wrong
company is a breach, and nobody finds out from a log.

When no customer is in scope - every request today - it reads the environment
variable exactly as before. Proven:

  single tenant today
    from : Rock Roofing <onboarding@resend.dev>          unchanged
    link : https://app.rockroofing.co.uk                 unchanged

  Rock, resolved
    from : Rock Roofing <notifications@constructionliberation.com>
    link : https://app.rockroofing.co.uk

  Wilson, resolved
    from : Wilson Construction <notifications@constructionliberation.com>
    link : https://wilson.constructionliberation.com
    -> reads as Wilson to the subcontractor, links to Wilson's portal

  a customer set up incompletely
    THROWS: Customer "broken" has no senderName configured. Refusing to fall
    back to another customer's value.


ON SENDING DOMAINS - the decision this encodes
----------------------------------------------
One verified sending domain, with a per-customer sender NAME and the customer's
own address as reply-to. To the subcontractor it reads as their client's email;
hitting reply writes to them, not to you.

The alternative - a subdomain per customer - means a DNS and verification job
each time, which is the thing you decided to avoid, and spreads sending
reputation across many new domains. Spam filters trust one domain with a long
clean history far more than fifty new ones.

WHAT TO CHECK AFTER DEPLOYING
-----------------------------
The only risk here is an email going out from the wrong address or not at all.

1. Send a variation to yourself. Check it arrives and the FROM address is
   exactly what it was before.
2. Send an application to yourself. Same check - that one uses the commercial
   sender, which is a different address.
3. Press Report a Problem. Confirm it reaches you.
4. Lock a WIP month, if convenient, and confirm the notification arrives.
5. Pre-start email to yourself if you can raise one.

If any email fails to send, tell me which - that would mean I have mapped one of
them to the wrong sender kind.
