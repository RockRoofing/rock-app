"IT IS STILL SHOWING THE PIPEDRIVE ONES" WAS THE ANSWER
--------------------------------------------------------
That one detail identified it. Imported activities showing while yours do not is only
possible in one place.

When I unified the storage in pkg331, the deal started being saved with:

    activities: []

So on every page load, deals came back with NO activities at all. Imported ones still
appeared because they live in the separate outstanding list. Yours could only appear if
that list had been rebuilt to include them - one extra step, on a different request, that
had to succeed every time.

Before pkg331 your activities came straight off the deal and always showed. That is
precisely the behaviour you described losing.

I did that to myself: pkg331 was meant to end this class of bug and instead caused the
exact symptom you had been reporting all along.


THE FIX
-------
Activities and notes CREATED IN THE CRM are stored on the deal again. IMPORTED ones are
still stripped - there are 36,824 of them, they have their own per-deal stores, and
re-saving them is what caused the 413s.

That distinction is the whole point:

    imported (36,824)     -> per-deal stores only, never on the deal
    created here (a few)  -> on the deal, and mirrored to the same store

Keeping the handful you create costs nothing and means an activity you add is on the deal
you added it to - which is where every view looks first. No aggregate has to be rebuilt for
it to appear.

Verified end to end: an activity added in a deal survives the save, the imported ones are
still dropped from the deal record, and after a reload the table shows both.


WHAT TO DO
----------
Deploy, then add an activity in a deal and check the Activities tab. It should be there.
Anything you added earlier that is still on a deal will also reappear, because those
records were never removed from the deals that failed to save - only from ones that saved
successfully after pkg331.
