pkg857 - Project report download: rewritten
===========================================

ONE FILE.  pages/api/project/[id]/report.js

Folder uses literal square brackets. No new files to create by hand.

THIS ONE DOES CHANGE WHAT YOU SEE. The report currently downloads with two
empty tabs and some wrong summary figures. It will now be populated and correct.


IT WAS NOT THE DEPLOY
---------------------
Checked first. The only change pkg856 made to this file was the withTenant
wrapper, and that wrapper is dormant. This has been broken for a long time -
almost certainly since the app moved off Xero Projects, which is why you have
never had a reason to use it.


FOUR FAULTS, COMPOUNDING
------------------------
1. It imported getProjectExpenses and getProjectInvoices from lib/xero.js.
   NEITHER IS EXPORTED FROM THERE. Only getXeroProjects is. Both calls threw on
   the first line.

2. Both sat inside `try { } catch (e) {}` with an EMPTY catch. So the throw was
   swallowed, costs and invoices stayed as empty arrays, the sheets were built
   with headers and a zero total, and the file downloaded looking completely
   normal. A silent catch turned a broken import into a plausible report. This
   is the same failure shape as everything else that has gone wrong on this
   project: no error, no alarm, just a wrong answer that looks right.

3. It read the Xero PROJECTS api (/projects.xro/1.0/projects). Rock has never
   used Xero Projects - the app works from TRACKING CATEGORIES, via
   getProjectsFromCategories, in 18 other files. So the project lookup returned
   nothing, jobNo came out as an empty string, and even a working invoice
   lookup would have been searching for a blank job number.
   report.js was the LAST FILE IN THE CODEBASE still on that path.

4. Labour Spend was hardcoded to 0 and Materials Spend was set to ALL costs. So
   the summary was wrong as well, not only the two empty tabs.


WHAT IT DOES NOW
----------------
It reads the SAME RECORD Project Financials displays and formats it. It does not
recompute AFA, margin, WIP, costs or invoiced.

That is deliberate. A second implementation of a rule is how this project has
produced nearly every wrong number it has ever had - the same rule written twice
and left to diverge. The report cannot disagree with the screen, because it is
reading what the screen read.

That record also carries the cost and invoice LINES, so Expenses and Income come
from the same single read. NO XERO CALL AT ALL, which makes it faster and
removes the token refresh that used to be the first thing able to fail.

Also changed:
  - Variations use the STORED variation number where there is one, not the row
    position. Numbering by position is how a V03 quietly becomes a V02.
  - Variations read through projectVariations(), the single rule for which of
    the two possible variation records wins.
  - Dates written as "30 Nov 2026", not 30/11/2026. Unambiguous in any market,
    which matters for the same reason the cash flow dates did.
  - Expenses and Income sorted oldest first.
  - Income splits Total, Paid and Due.
  - If the data has not been built, it returns a clear message instead of an
    empty workbook.

WHAT TO CHECK AFTER DEPLOYING
-----------------------------
1. Open a project with costs and invoices on it. Download the report.
2. Expenses tab - lines present, total matches Total Costs on the Summary tab.
3. Income tab - invoices present, total matches Gross Invoiced on the Summary.
4. Summary tab - AFA, Gross Invoiced, Margin and WIP MUST MATCH what Project
   Financials shows for that project on screen. That is the whole point of the
   rewrite, so if any of them differ, tell me which.
5. Try a project with no costs yet - you should get "No cost lines recorded
   against this project" rather than a blank tab.


NOTE
----
The report reads the dashboard snapshot, which is rebuilt when Project
Financials is opened and cached for a few hours. So a download taken right after
a sync may lag the sync until Project Financials is opened once. That is the
same data the page itself shows, which is the point - but worth knowing so it is
not mistaken for a fault.
