THE FAULT
---------
cashflow.js held TWO definitions of "today":

  line 19    const todayISO = new Date().toISOString().slice(0, 10)   // UTC
  line 972   const todayIso = isoDay(new Date())                      // viewer's
                                                                      // LOCAL date

Same word, same file, two answers. Proven at the moment of building this
package:

  instant                2026-09-12T23:05Z
  todayISO   (UTC)       2026-09-12
  todayIso   (NZ local)  2026-09-13     <- one day apart, right now

In the UK these agree for 23 hours a day, which is why this has never been
seen. Viewed from New Zealand, UTC+12, they are DIFFERENT DATES FOR TWELVE
HOURS OF EVERY DAY.

todayISO decides what counts as already past, so it decides what money falls
inside the 13 weeks: line 806 whether an application period has been earned,
3104 which scheduled sales are still future, 3209 and 3293 what is overdue.
Move the date by a day and money moves in or out of the window. None of it
touches Outstanding Invoices, which is a position and does not care what day
it is. That is exactly the asymmetry you spotted.

SECOND FAULT ON THE SAME LINE: todayISO was a module-scope const, computed ONCE
when the page loaded and never again. A tab left open overnight kept yesterday's
date indefinitely while the other today kept moving.


THE FIX
-------
New lib/businessDate.js exports businessToday(tz). It returns YYYY-MM-DD for
now in the BUSINESS'S timezone, currently Europe/London, whoever is looking and
wherever they are.

That is the right rule. A valuation date, a payment date and a VAT date are
facts about the business. A figure must not change because someone opened it
from a different country.

In cashflow.js:
  - todayISO is now a FUNCTION, so it cannot go stale on an open tab
  - all six read sites call todayISO()
  - line 972's todayIso now calls the same function instead of the local-date
    helper

23 changed lines. Nothing else in the file moved.

Built with Intl.formatToParts rather than a locale string, because locale
output varies by runtime and a date silently coming out DD/MM is the same class
of bug this file exists to end. Falls back to UTC if Intl is unavailable -
wrong by at most a day, never undefined, which is the failure that actually
breaks a comparison.


CHECKS I RAN
------------
- esbuild compile on both files: 0 errors
- no bare todayISO left anywhere - all six sites call it
- no new non-ASCII characters
- ran the old and new rules against the same instant across three timezones and
  confirmed the old two disagree and the new one does not


WHAT TO EXPECT - THIS WILL MOVE THE CLOSING BALANCE
---------------------------------------------------
For roughly twelve hours of your day in NZ, the cash flow has been evaluating
"has this period passed" against the WRONG DAY. Correcting that moves the
number, and the new number is the right one.

Before deploying, note the closing balance. After deploying, note it again.
A change is expected and correct. Tell me the two figures.

The cleanest confirmation that it is now stable: check it again around 12:05
NZ time. Under the old code the number would shift at that point, as UTC
crossed into the next day. Under the new code it will not.
