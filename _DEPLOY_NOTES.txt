pkg302 - CRM: Activities and Notes import
==========================================

CHANGED FILES
-------------
  lib/crmImportMap.js     mappers + detection for the two new exports
  pages/api/crm.js        per-deal storage for activities and notes
  pages/crm.js            import screen accepts and routes them

No new files. All straight replacements. Independent of every other package.


WHY IT SAID "UNRECOGNISED FILE"
--------------------------------
detectExportType() only knew three exports. It looks for 'Deal - ID', 'Organization - ID'
or 'Person - ID' - the hyphenated style the deals/orgs/people exports use.

The activities and notes exports use PLAIN headers: 'ID', 'Subject', 'Deal ID', 'Content'.
Nothing matched, so it refused the file rather than importing it wrongly - which is the
right failure, just not a helpful one.

Both are now detected. They share a plain 'Deal ID' column, so they are told apart on
their own distinctive ones: 'Subject'/'Marked as done time' for activities, 'Content' for
notes.

                                              2,577 skipped (no Deal ID)

The skipped rows are activities and notes attached to an organisation, person or lead
rather than a deal. There is nowhere to hang them in the CRM, so they are counted and
reported rather than silently dropped - the message tells you how many.

Dates, the Done flag and assignee all verified against real rows.


HOW IT STORES THEM
------------------
One key per project - crm:activities:<dealId> and crm:notes:<dealId> - as agreed. Opening
a deal reads only that deal's records instead of pulling 36k rows to show five.

Grouping happens in your browser BEFORE sending, so each project arrives in exactly one
request and each key is written outright. No read-modify-write, and re-running a failed
import is safe.

Chunked by PROJECT (120 per request), not by row. Writing one key per project means a
large chunk is a lot of database writes in a single request, which is what would time out.
53 requests for activities, 52 for notes. Largest payload measured: 0.30MB against the
~4.5MB limit, so there is plenty of headroom.

An index key (crm:activities:index) records which projects have records, so the next
wipe-and-replace import can clear the old ones without scanning the whole database.


IMPORT ORDER MATTERS
--------------------
Activities and notes attach to deals by Deal ID, so import DEALS FIRST. If you re-import
deals later, re-import these two afterwards as well.

Each import is still wipe-and-replace within its own type: importing activities replaces
all activities and leaves deals, companies, contacts and notes alone.


NOTE ON WHAT IS IMPORTED
------------------------
This brings in EVERYTHING, not the open-deals-only subset scoped previously (which would
have been ~2,541 activities and ~662 notes). You said you were uploading all the data, so
the full history comes across. If it turns out to be too much, filtering later is easy -
but importing it now means nothing is lost.
