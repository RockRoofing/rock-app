1. WHY SOME COMMENT BOXES WOULD NOT ACCEPT TYPING
--------------------------------------------------
Nothing was wrong with the boxes. Every note was in the deal TWICE.

Opening a deal ran the sub-record load twice:

    openDealById  ->  loadDealSubs(id)                      (first merge)
                  ->  router.push(?deal=id)
                          -> the router effect fires
                          -> loadDealSubs(id) again          (second merge)

The merge appended blindly, so every imported note and activity went in twice - with the
SAME id both times. React uses those ids as keys, and duplicate keys make sibling
components share state. That is why one comment box would take typing and the identical
one below it would not: two elements fighting over one key.

It looked random because it depended on which note you happened to click, and it varied
between sessions.

FIXED TWO WAYS:
  - the merge is now by id, so running it twice changes nothing (proven on the bench:
    merge once, twice, three times - same 2 history entries, no duplicate ids)
  - openDealById no longer calls it at all, since the router effect already does

Nothing was corrupted in the database. Imported records are stripped before saving
(the h_pd_ filter in leanDeal), so this only ever existed in the browser. Reloading the
page was, unknowingly, the workaround.

Keeping the existing entry on merge also protects comments: the imported branch hard-codes
comments:[], so a second merge would have wiped any comment added to an imported note.


2. MENTIONS USE FULL PORTAL USER NAMES
--------------------------------------
The pool is pre-contract plus admin portal users - the same list that decides who can own
a CRM activity. Full names throughout: the autocomplete lists them, and picking one
inserts "@Edita Durikova", not "@Edita".

Typing a full name by hand now works too. The suggestion box used to give up at the space,
so "@Edita Dur" stopped suggesting; it now allows one space after the @.

A FIRST NAME still resolves, but ONLY where exactly one person has it. If you ever have
two Jameses, "@James" on its own notifies nobody rather than picking one - guessing who to
email is worse than not emailing. "@James McVeigh" and "@James Bell" both work. Usernames
work too.

Tested:
    "@Edita Durikova please look"      -> Edita Durikova
    "@Edita"                           -> Edita Durikova   (only one Edita)
    "@James"  with two Jameses         -> nobody
    "@James McVeigh"                   -> James McVeigh
    "@jamesb"                          -> James Bell
    "mail me at jm@rockroofing.co.uk"  -> nobody           (an address is not a mention)

The same rule is applied in two places - the browser, which decides what the history line
says, and the server, which decides who gets the email - so they cannot disagree.
