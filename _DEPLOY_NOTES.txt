THE RULE, IN ONE PLACE
=======================
resolveGrossAfa() in lib/applications.js is now the only place the order of
preference is written. The dashboard, the project page and the project API all call
it. It was written four times before, in three different orders.

  1. the figure STAMPED by the latest sent application   - as issued, no arithmetic
  2. rebuilt from the latest sent application            - only where nothing was stamped
  3. a stored override                                   - ONLY where there is no sent
                                                             application at all
  4. project details

A stored override can no longer beat a sent application on any surface.

Note there is no manual override field anywhere in the UI. Every afaOverride was
written by an application send, so an override reaching step 3 is always a leftover
from an earlier one.


WHAT WAS ACTUALLY WRONG
------------------------
pages/api/project/[id].js line 132 read:

    const afa = (settings.afaOverride != null && isFinite(settings.afaOverride))
      ? Number(settings.afaOverride) : (contractValue + instructedVars)

No application preference at all. A stale override was authoritative. That endpoint
feeds Project Financials and the project report, so those two could contradict the
retention register on the same job - and would do so on exactly the projects where
an override had been left behind by an earlier send.

It also still used the truthy `v.instructed` test that pkg799 replaced everywhere
else, so variations recorded as the string 'no' counted as instructed there. Both
fixed. The endpoint now returns afaSource as well, so the figure can be traced.

pages/project/[id].js additionally ignored prevCertGross when working out previously
certified - it recomputed from the preceding application. Now the same rule as the
certificate and the register.
