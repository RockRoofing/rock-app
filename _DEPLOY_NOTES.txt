THE CHANGE
===========
"Add photos" is now "Add documents / images", and the panel is "Documents & images".

  IMAGES   drawn onto the page as before, captioned with the file name.
  PDFs     their pages are COPIED IN WHOLE. A supplier quote or a marked-up drawing
           arrives as part of the variation document rather than as a link the
           customer has to go and find. The file name is printed at the top of its
           first page so it is clear which attachment they are looking at.

Everything still flows through buildVariationPDF, so Download, Send to customer and
the instruction email all carry them without any of those paths changing.


DETAILS WORTH KNOWING
----------------------
THE CAMERA ATTRIBUTE IS GONE. The input carried capture="environment", which sends
a phone straight to the camera and hides the file browser. That is right for photos
and wrong the moment a PDF is allowed, because a camera cannot produce one. The
camera is still one tap away inside the normal picker.

A PDF DOES NOT RENDER IN AN <img>. It shows a broken-image icon, which reads as
"this upload failed". Anything that is not an image now gets a labelled tile with
its extension instead, and the thumbnail strip says underneath which of the two it
is: "merged into the PDF", or "listed, not merged".

FILE TYPE IS READ FROM THE NAME, not a stored mime type. Records written by pkg817
carry no type at all, so anything keyed on that would have come out unknown for
every attachment already uploaded.

THE STORAGE KEY IS STILL builder.photos. It is the wrong name now, but it is what
pkg817 wrote and variations already hold it - renaming it would strand those.

A PDF THAT WILL NOT PARSE says so on the page rather than being skipped, the same
as one that will not download. A variation quietly missing its evidence, with
nothing to say any was meant to be there, is worse than a line admitting it.

ONE THING I HAVE NOT DONE
--------------------------
A Word file or a spreadsheet cannot be merged into a PDF, so it is listed by name
and nothing more - which means it does NOT reach the customer. The picker still
accepts them, because having them on the variation in the portal is useful even
when they cannot be printed into the document.

If they should actually go out, the right answer is to attach them to the EMAIL
alongside the PDF - variation-send.js already builds an attachments array, so it is
a contained change. Say the word. Until then, anything that must reach the customer
should go on as a PDF or an image.
