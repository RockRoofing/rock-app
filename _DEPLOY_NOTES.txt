THE ANSWER: IT IS MY pkg797 MERGE, NOT THE FORMULA
====================================================
I checked the obvious suspects first and ruled them out:

  buildAppVariations() returns app.variations unchanged once an application is
  SENT, so the page and the register use the SAME frozen variations.

  rows on the page is initialised straight from appProp.contractWorks, so they use
  the same contract works too.

Same function, same inputs - so the two could not disagree. Unless they are not
reading the same COPY of application 2. They were not.

pkg797 taught the dashboard to read applications from BOTH settings records, because
project settings are keyed by tracking option id OR job number. Where both records
hold the same application, it had to choose, and the tiebreak I wrote was:

    (a.status === prev.status && (a.contractWorks || []).length > (prev.contractWorks || []).length)

Whichever copy had MORE contract-works rows. That is not a measure of currency. On
J228 it picked a copy carrying an extra 29,405.50 of works, so the register
recomputed 169,679.70 while the application page showed 140,274.20 - both from
computeApplicationSummary, on two different copies of application 2.

Reproduced exactly:

    old tiebreak picks -> 169,679.70
    new tiebreak picks -> 140,274.20     matching your screenshot

THE FIX: the id record's copy always wins. The applications page loads one record,
getProject(projectId), keyed by the tracking option id - so that copy is the one
whose figures are on screen, and the register must read the same one. The
job-number record now only fills gaps, which is what pkg797 was actually for.

A THOUGHT FOR AFTER THIS
-------------------------
Duplicate project records are the root of this, the missing variations, the invisible
applications and the stray afaOverride stamps. Every one of those was one record
shadowing another. Worth a one-off script that lists every project holding settings
under BOTH keys and what differs between them - it would turn a recurring class of
bug into a finite list. Say the word.
