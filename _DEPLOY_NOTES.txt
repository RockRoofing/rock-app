WHY IT STOPS AT 120 - AND WHY IT IS NOT THE MISSING DEALS
-----------------------------------------------------------
It is not the pipeline change. Records whose deal is not in the CRM are filtered out in
your browser BEFORE anything is sent, so a missing deal just shortens the list. It cannot
stall the import.

120 is the chunk size in the version you are running. So it fails on the FIRST request.

That first request does the wipe, and on the old code the wipe blanked every key left by
the previous import - one at a time:

    6,261 keys x ~35ms  =  ~219 seconds, plus the 120 projects themselves
    against a Vercel function limit of 10-60 seconds  ->  timeout

Your first activities import (pkg302) worked because there was nothing to wipe. It left
6,261 keys behind, so every attempt since has died on that wipe. It worked once and has
failed ever since - which matches what you have seen.


THE FIX
-------
  - The wipe now only clears keys that will NOT be rewritten by this import. Re-importing
    the same file clears nothing at all, so the first request is no heavier than any other.
  - Writes run 25 at a time instead of one after another.
  - The index and board summary are computed in your browser and sent once at the end,
    rather than read and rewritten on all ~45 chunks.
  - maxDuration raised to 60s on the CRM endpoint as a safety net.
  - Chunk size 120 -> 300 (19 requests instead of 46), largest payload 0.76MB against the
    ~4.5MB limit.

Estimated database time for the activities import: ~196s down to ~8s.
