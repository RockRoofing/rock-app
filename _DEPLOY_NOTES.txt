WHAT I GOT WRONG
=================
A day cell in ops:planning-allocations is not always an array. It is the legacy

    [ { opId, half } ]

on older records, and

    { status, unnamed, entries: [ { opId, half } ] }

on anything written through the newer path. planning.js already has cellEntries()
for precisely this, with a comment saying so, and every other action in the file
uses it. My move action did not - it called .find() straight on the cell, so on any
project whose cells had been through the newer path it threw.

The whole action is rewritten:

  READING goes through cellEntries(), so both shapes work.

  WRITING puts the cell back in the shape it was already in. Writing an array where
  an object was would have flattened it and silently dropped that day's `unnamed`
  count and its provisional/confirmed status - a worse bug than the crash, because
  nothing would have told you.

  EMPTYING a day only deletes it when there is nothing left at all. A cell still
  carrying unnamed slots is kept, with its entries emptied.

Verified against both shapes:

  object cell, full day moved   -> moves; unnamed 2 and status kept on the old day
  array cell, full day moved    -> moves; empty day and empty project cleaned up
  am moved onto own pm (object) -> merges to a full day; target's unnamed kept
  moving onto another project
  the person is already on       -> refused as a clash
