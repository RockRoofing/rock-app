YES - AND IT WAS IN ABOUT TWENTY PLACES
=========================================
Your instinct was right, and checking turned up something worse than the original
bug. `instructed` is stored as a BOOLEAN by the tracker, its modals and Edit Project
Details, and as the STRING 'yes'/'no' by the Variation Builder. Around twenty
readers then tested one shape or the other, so roughly half were wrong about any
given variation - in BOTH directions:

  TRUTHY TESTS (`v.instructed`)          the string 'no' is truthy, so a
                                         not-instructed variation read as INSTRUCTED

  STRING TESTS (`v.instructed === 'yes'`) a boolean true failed, so a variation
                                         instructed from the tracker read as NOT
                                         instructed

THIS IS WHY YOUR TWO SCREENSHOTS DISAGREED. V14 and V15 really are stored as not
instructed - the builder withdrew them. The operations report used the correct test
and told you the truth. Edit Project Details used

    <select value={v.instructed ? 'yes' : 'no'}

so the string 'no' came out truthy and it displayed "Instructed". Project
Financials did the same thing with `vars.filter(v => v.instructed)` and counted the
money. Two screens were lying and the one you doubted was right.


FIXED, AND THE SERIOUS ONES FIRST
-----------------------------------
Three of these were not cosmetic:

  settings.js       `if (was.instructed !== 'yes') continue` is the lock that
                    REFUSES a change to an instructed variation. Against a boolean
                    it never engaged, so an instructed variation could be edited or
                    deleted with no refusal at all.

  variation-instruct.js  the guard stopping a customer instructing the same
                    variation twice. Same test, same failure - a second click on the
                    link would have recorded a second instruction.

  cron/variation-reminders.js  skips variations already instructed. Against a
                    boolean it did not skip, so the customer was chased to instruct
                    something they had already instructed.

Plus the display and totals: the project report and its Excel, project financials,
Edit Project Details, the variation tracker, the CM site forms, the schedule form,
the project report PDF, the application PDF, and two more inside the builder.

The project-cashflow pair is deliberately untouched: the API normalises once and the
client reads that contract, which is the pattern the rest of this should have
followed.

pkg815's builder change is in here too - it now writes a BOOLEAN, which is only safe
because every reader above was fixed in the same package. On its own it would have
broken every string test.


NO LONGER POSSIBLE
-------------------
pages/api/project/[id]/settings.js is the only write path for variations, and it now
coerces `instructed` to a boolean on the way in. The stored data converges as records
are saved and no future reader has to know there were ever two shapes.

The lock's change-signature uses isInstructed too - otherwise an untouched variation
stored as 'yes' would compare unequal to the same variation now holding true, and the
lock would refuse a save that changed nothing.


AND NO, YOU DO NOT HAVE TO FIX THEM BY HAND
=============================================
  pages/api/admin/variations-instructed-audit.js       admin only

  GET                          report only, changes nothing
  POST { "apply": "shape" }    convert every stored string to a boolean
  POST { "apply": "restore" }  the above, plus re-instruct where there is EVIDENCE

Two jobs, deliberately separate:

  SHAPE is lossless. 'yes' meant instructed and always did, so it is converted
  without asking.

  MEANING is not. Once the builder wrote 'no' over an instruction, the record no
  longer says it was ever instructed, and nothing in it distinguishes "withdrawn by
  the bug" from "genuinely never instructed". So this does not guess. It looks for
  evidence:

    - a SENT application whose frozen copy of that variation says instructed. An
      application that went to the customer that way is proof it was instructed.
    - the OTHER settings record for the same project saying instructed, where a
      project is held under both a tracking id and a job number.

  Anything with evidence is listed WITH the evidence and only changed on
  apply: "restore". Anything that came from the builder, is not instructed, and has
  no evidence is flagged "review suggested" and never touched automatically -
  re-instructing those blind would inflate the final account on jobs that were never
  instructed at all.

Run the GET first and read it. It reports per variation: the project, the number,
what is stored, the shape fix, any evidence, and the value at stake.
