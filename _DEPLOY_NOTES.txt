1. WHY THE VARIATION WOULD NOT DELETE - not a fault
---------------------------------------------------
pages/api/project/[id]/settings.js refuses to remove a variation the customer
has already instructed:

    Refused: V02 has been instructed and cannot be removed.

You instructed V02 when you tested the instruct link. The guard is correct - the
customer authorised that scope at that value, so it cannot be quietly deleted.

THE ACTUAL FAULT IS THAT YOU COULD NOT SEE IT. deleteVariation never checked
whether the save succeeded, so the 409 and its message went into console.error
and the row just sat there. The guard was working; only the reporting was
missing.

Now it shows the server's own message. The instructed toggle a few lines above
threw its reply away for the same reason and hits the same guard, so that is
fixed too.

2. THE APPLICATION THAT SHOWS IN THE TABLE BUT NOT IN THE PROJECT
-----------------------------------------------------------------
That symptom is diagnostic in itself. The two views read differently:

    getAllProjectSettings()   scans EVERY project:* key and returns each record
                              under whatever key it is stored at. The summary
                              table therefore finds everything.

    getProject(id)            reads ONE exact key. The per-project view finds
                              only the record stored under the id the page asked
                              for.

So a project whose settings exist under BOTH its Xero tracking option id AND its
job number will show its applications in the summary and hide them when you open
the project. Nothing errors. The application is not lost - it is under the other
key.

This is the duplicate-record fault that has caused at least four separate
problems on this project and has been sitting on the open-items list since the
handover as "a script listing every project holding settings under BOTH keys -
worth enumerating once".

This is that script:

    /api/admin/project-key-audit

READ ONLY. It writes nothing. It lists every project record, pairs them up by
the job number each one claims, and reports any job number holding more than one
record - with what each side holds, so you can see which record a page is
actually reading.

Add ?full=1 to see every record rather than only the duplicated ones.

RUN IT AND SEND ME THE OUTPUT. I am not going to guess at the fix. Whether the
right answer is to merge the pair, point the page at the other key, or stop the
duplicate being created in the first place depends on how many there are and
which side holds what - and that is a decision about your data, not a tidy-up.

Do not change anything based on it yet.
