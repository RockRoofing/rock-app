PART 1 - SEEDING FROM THE LATEST APPLICATION
--------------------------------------------
The pop-out only ever looked at previous FORECASTS:

  const prev = (d.hypApps || []).sort(...).pop()

It never read the project's real applications. So on a live job applied for three
times, a new forecast started every rate line at 0% and you keyed the position in
by hand.

It now seeds percentages, MCD and retention from the latest real application, and
falls back to contracted rates at 0% when there are none. The API returns a new
`latestApplication` - highest seq, trimmed to the fields the seed needs.


PART 2 - THE BIT YOU CAUGHT
---------------------------
The percentages are CUMULATIVE value to date. Everything below the last
certificate has already been applied for and must not be spread again.

prevGross - the figure that turns cumulative into "this cert" - looked at
forecasts only:

  const others = hypApps.filter(a => a.id !== editId)

So on a live job with real applications and no forecasts yet it returned ZERO,
and the entire value to date went out as this period's revenue. Seeding the
percentages in Part 1 is exactly what exposed it: before, the rows started at 0%
so there was nothing to double count.

prevLabourToDate had the same forecasts-only lookup, so labour was over-stated
the same way.

Both now use one shared `prior` - whichever certificate ENDS LAST before this
period starts, real application or earlier forecast. It has to be the same rule
as the seeding, or the figure carried IN and the figure deducted would disagree.

Worked through, with 2.5% MCD and 5% retention:

  Value to date now          1,000.00
  Already claimed              600.00
  Increment                    400.00
  This period (revenue)        370.50     <- 400 less MCD, less retention

  What it did before           926.25     <- the whole job, re-spread


DETAILS WORTH KNOWING
---------------------
THE PRIOR IS VALUED ON TODAY'S RATES. applyPriorPct() copies only the
percentages off the prior certificate and re-values them against the current
seed rows. If it used the prior's own stored totals, any rate change since would
land in this period as though it were newly built work.

VARIATIONS ARE EXCLUDED ON BOTH SIDES. The forecast carries no variations
(workApp passes variations: []), so counting them in the prior would understate
what has been claimed and inflate this period.

TIES GO TO THE APPLICATION. If a forecast and an application end on the same
date, the application wins - it is the certified position.

DRAFTS COUNT as the latest application. A draft is still the most recent view of
percentage complete, and this is a forecast. The banner names which application
was used and its status.

ROWS MATCH ON ID THEN CODE, in both the seeding and the prior. Ids normally line
up because both come from buildContractWorksFromRates(), but re-uploading the
rates regenerates them and the code is then the only stable handle. Without the
fallback every line would read 0% and look like a job that had never started.

NEGOTIATED PROJECTS (N:<dealId>) have no real applications and still start from
contracted rates. Unchanged, and correct.


ONE DECISION YOU MAY WANT TO OVERRULE
-------------------------------------
"Latest application, else contracted rates" taken literally breaks the second
forecast on a project: application 3 certifies at 40%, you forecast April to
60%, then open May - and May would drop back to 40%, silently undoing April.

So the rule is WHICHEVER PERIOD ENDS LAST. With no forecasts yet, which is your
case, it behaves exactly as you asked. Say the word if you want it strictly the
application every time.


ALSO FIXED WHILE IN THERE
-------------------------
The modal closed on a backdrop click and had no Escape handler - against your
standing rule. It holds a period, percentages across every rate line, materials
lines and payment terms, and a stray click outside threw the lot away. Backdrop
no longer closes; Escape does.


ON SCREEN
---------
A line at the top of a new forecast says where the percentages came from:

  blue   "Percentages carried over from Application 4 (sent) - the latest
          application on this project."
  blue   "Percentages carried over from the previous forecast, which runs later
          than the last application."
  amber  "No applications yet - starting from the contracted rates at 0%."

Otherwise a seeded figure and one somebody typed look identical. It does not
show when editing an existing forecast, which loads its own saved values.


WHAT TO CHECK ON DEPLOY
-----------------------
Open a forecast on a live job that has had applications. The percentages should
arrive already filled in, and "Revenue this period" should be roughly the next
slice of work - NOT the whole contract to date. Any forecasts you saved before
this package were built on the old maths and are overstated; delete and redo
them.
