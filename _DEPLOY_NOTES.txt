pkg284 - Project Finance: stop depending on the dashboard snapshot
===================================================================

CHANGED FILES
-------------
  pages/api/cm-project-financials.js      rewritten to read the source stores directly
  pages/forms/cm/project-finance.js       resolves xeroId first; reports failures properly
  middleware.js                           INCLUDED so the passthrough is definitely present

middleware.js is in this package deliberately - see cause 1 below.


WHY IT STILL DID NOT WORK
--------------------------
My pkg282 fix was correct as far as it went, but it was not the whole story. There were
up to three separate things that could each produce "no financial data", and I had only
fixed one of them. Rather than guess at which one you hit, this removes all three.

1. MIDDLEWARE. /api/cm-project-financials must be in the Site App passthrough or the
   request is rewritten to the /forms page and never reaches the API. That passthrough was
   added in pkg281. pkg282 contained only two files - so if you deployed pkg282 WITHOUT
   pkg281, the route was still blocked and my fix could not run at all. middleware.js is
   included here so that cannot be the problem regardless of what you have deployed.

2. THE SNAPSHOT MIGHT NOT EXIST. The old code needed dashboard:cache to be populated. It
   expires after 4 hours, so if nobody had opened Project Financials recently there was
   simply nothing to read.

   The page now resolves the project's Xero id through /api/dashboard first - exactly what
   the CM Applications screen already does, including the ?sync=true retry. That endpoint
   REBUILDS the snapshot when it is stale. The API then reads the underlying stores
   directly (project:<xeroId>, costs:latest:<xeroId>, costs:lines:<xeroId>,
   invoiced:lines:<xeroId>), so it no longer depends on the snapshot's shape, freshness or
   existence at all.

3. THE CONTRACTS MANAGER CHECK COULD FAIL WRONGLY. The old check compared your name to the
   CM on the FINANCIAL record, which is a different field, populated differently, from the
   one the Site App uses to decide which projects are yours. A project could therefore
   appear in your list and then refuse to open.

   It now checks the OPS project list first - the same source the app itself uses - and
   accepts the financial record's CM as a fallback. The two can no longer disagree.


ALSO: FAILURES NOW SAY WHAT HAPPENED
-------------------------------------
If the response is not JSON, the page now says the service could not be reached and names
the middleware passthrough as the cause, instead of a vague "could not load". If it IS
JSON, the API's own message is shown. So if this still misbehaves, the screen should tell
us which of the above it is rather than us guessing again.

Spend also has a fallback: if the aggregate cost cache is empty but cost lines exist, the
lines are totalled, so the page will not show zero spend against a real cost history.


WHAT YOU SHOULD SEE
--------------------
Margin (EOM basis, last completed month's valuation date, inc WIP), then labour, materials
and total budget vs spend vs remaining, then the costs table with Labour / Materials / All
tabs.

If a project has no valuation date set for last month, margin shows a dash and says so -
that is correct behaviour, not a failure. The budgets and costs still show.
