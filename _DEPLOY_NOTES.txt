GOOD CATCH - AND THERE ARE TWO CASES
------------------------------------
WHERE THE FORECAST HAS matItems, the line's own term is ALREADY honoured and
always has been. payDate was computed at save from that line's term, so a 60-day
line pays at 60 days. The +30 path never runs for these.

WHERE IT DOES NOT - the legacy records - the term is NOT RECOVERABLE. Only
matDeliverDay and materialsThisPeriod were saved; the line items that carried the
terms were not. There is no materials term at forecast level either - only
salesTerm and labourTerm are stored.

So for legacy forecasts any figure is a guess. Rather than bury 30 in the code it
is now a SETTING - "Legacy materials, eom + days" beside the VAT rate:

    legacy delivery 25/09, materials 70,000
      eom + 0   pays 30/09
      eom +30   pays 30/10
      eom +60   pays 29/11

Set it to whatever your usual supplier terms were when those forecasts were built.

AND THE ESTIMATE IS FLAGGED. In the Project sales drill-down a materials figure
derived this way carries a small amber "est", hovering to say the payment date was
estimated rather than taken from the line's own term. So you can tell a real date
from a guessed one at a glance.


ALSO IN THIS PACKAGE
--------------------
pkg619 - the API had NO fallback for labour or materials on older forecasts, only
for sales. So sales came through and costs did not, which is the whole "income
with no spend" problem. Labour now falls back to labourDate + labourThisPeriod
exactly as the project page does, and materials are rebuilt from matDeliverDay +
materialsThisPeriod.

pkg618 - ONE bill on a project was discarding EVERY forecast cost for that project
that week. Now netted off instead, labour first.

payFromDeliver was declared inside the invoice-finance branch and used in the
cashflow branch - moved to module scope before it could throw.
