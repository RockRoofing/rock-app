ANSWER FIRST: THEY MAY WELL STILL BE THERE
--------------------------------------------
Variations live in TWO places - on the project record, and mirrored onto settings. I found
NINE readers across the tracker and the builder, each with its own precedence:

    line 227   project first
    line 284   settings first
    line 410   project first
    line 766   project first

Some preferred one copy, some the other. So two parts of the same page could legitimately
disagree about how many variations a project has - and an overwrite of ONE copy makes them
vanish from a reader that prefers it while the other copy sits there untouched.

ONE RULE NOW: whichever list has more rows wins.

Not "project first" or "settings first" - either of those loses data whenever the other
copy is the fuller one, which is precisely what happened. Tested: with one copy wiped and
the other intact, all the variations come back.

So there is a real chance this deploy restores them on its own.


CHECK BEFORE ASSUMING THE WORST
---------------------------------
Console on any portal page:

    fetch('/api/variation-debug').then(r=>r.json()).then(console.log)

Every project with variations, and how many are in EACH place:

    { projectId, jobNo, name, onProject: 7, onSettings: 1 }

If onProject and onSettings differ, nothing has been lost - a reader was looking in the
wrong place, and this package fixes that.
If BOTH are low, those records are genuinely gone and would need re-entering.

For one project:

    fetch('/api/variation-debug?projectId=PUT_THE_XERO_ID_HERE')
      .then(r=>r.json()).then(console.log)

That lists every variation in both places - number, description, value, whether it was
built in the builder and when it was sent. It writes nothing.

Run it before doing anything else, and tell me what it says. It settles in ten seconds
what I have twice now had to guess at.
