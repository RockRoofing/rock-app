WHAT THIS FIXES, AND WHY NO WRAPPER COULD
-----------------------------------------
A serverless function stays warm and serves many requests. Anything cached at
module scope therefore outlives the request that put it there. withTenant scopes
the REQUEST; these four live outside it entirely, so nothing in pkg854-858
touched them.

  lib/msGraph.js    let cachedToken = null    Microsoft Graph access token
  lib/crm8x8.js     let cachedToken = null    8x8 access token
  lib/pipedrive.js  let _pipelineId = null    Pipedrive pipeline id
  lib/db.js         let store = {}            in-memory data fallback

Once each customer has their own Microsoft app, one company's Graph token cached
at module scope gets handed to the next request that arrives - and used to read
another company's mailboxes. Nothing errors. It simply works, on the wrong data.

Demonstrated, running the old and new code side by side:

  OLD, a single module variable
    rock caches its token
    wilson reads the cached token -> ROCK-TOKEN          LEAKED

  NEW, scoped cache
    rock caches its token
    wilson reads the cached token -> nothing             ok
    rock still has its own        -> ROCK-TOKEN          ok
    slots held: 2

  data store
    rock writes project:J244
    wilson reads project:J244     -> nothing             ok

  single tenant, as the app runs today
    no tenant in scope, reads back -> SINGLE             ok
    store works with no tenant                           ok


THE FIX
-------
lib/scopedCache.js provides a cache keyed by whichever customer is in scope.
Same code, one slot each.

Built once rather than written into four files, because the same rule written
four times and left to diverge is the fault class that has produced nearly every
wrong number on this project.

While single-tenant, no customer is in scope and everything uses one slot called
'single'. Behaviour today is exactly what it was.


WHAT THIS DOES NOT FIX - important
----------------------------------
The CREDENTIALS are still global. MS_CLIENT_SECRET, the 8x8 username and
password, and the rest come from environment variables - one set for the whole
deployment.

Keying the cache stops one customer being handed another's cached token. It does
NOT give each customer their own credentials. That is the separate job of moving
13 environment variables into per-customer settings, and it has to be done
before a second customer connects Microsoft, 8x8 or Resend. Listed here so it is
not mistaken for finished.
