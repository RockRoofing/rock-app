FIXED HERE - genuinely wrong on MCD
------------------------------------
1. SIX FUNCTIONS SHARED A PRE-MCD FALLBACK

   Each of these wrote the same expression:

       const fa = parseFloat(entry.finalAccount || entry.projectValue || 0) || 0

   projectValue is p.contractValue on project-derived rows - the ORIGINAL contract
   value, before MCD and before variations - and the imported "Gross AFA" column on
   imported rows. Both are gross.

   So wherever Final Account was blank, all six computed on the gross and came out
   high by the whole discount:

       calcVat                  VAT on the gross
       calcTotalDue             Final Account + VAT, both on the gross
       calcAccountRemaining     what is left to claim, on the gross
       calcFinalBalance         final-account balance, on the gross
       setRetStatus             the check that closes a retention, on the gross
       the inline row cell      Account Remaining as rendered

   Now one accountValue() function, used by all six. Final Account where there is
   one; otherwise gross LESS the MCD actually recorded; only raw gross where no MCD
   is known, in which case there is no discount to apply.

   On the test project a row with no Final Account moves from 1,000,000.00 to
   980,000.00.


2. ACCOUNT REMAINING WAS MEASURING AGAINST THE WRONG THING

   calcAccountRemaining read entry.appliedForLatest. The merge never carries that
   field onto a saved row - only project-derived rows have it - so on every saved
   row it was undefined and the function fell through to INVOICED. That is the exact
   thing its own comment says it must not do, because invoicing lags the application
   by weeks.

   It now reads entry.appliedFor, which is the value actually on screen. On the test
   project: 392,000.00, where it had been showing 580,000.00.


FLAGGED, NOT CHANGED - your call
---------------------------------
3. THE RELEASE HALVES ARE ON A DIFFERENT BASE FROM THE TOOLTIP

   calcReleaseHalf returns half of retention on APPLIED FOR. Both release column
   tooltips say "half of the retention on the FINAL ACCOUNT (Gross AFA less MCD x
   retention %)", and lib/applications.js computes halfRetention from finalSubTotal,
   which is what a certificate actually releases.

   pkg782 set the final-account basis deliberately. pkg785-787 rebased Retention
   Owed onto Applied for and this followed it - reverting that decision as a side
   effect rather than as a choice.

   This is NOT an MCD fault. Both bases honour the placement flags. It is a base
   fault, and it only shows mid-contract - the two converge once the job is fully
   applied for. On the test project at 60% applied:

       half on applied for    14,700.00   (what shows now)
       half on final account  24,500.00   (what the tooltip and certificate say)

   entry.retentionOnFinalAccount is already on the row, so switching is one line.
   Not done unasked - it moves the halves on every live project.


4. THE MCD PLACEMENT FLAGS DEFAULT DIFFERENTLY IN TWO PLACES

   Carried forward from pkg797 and still true. lib/applications.js treats a missing
   flag as TRUE (MCD applies to everything); pages/api/applications.js stamps
   `project.mcdOnVariations === true`, so a missing project setting becomes FALSE.

   An application created before these flags existed therefore computes with MCD on
   everything regardless of what Edit Project Details now says. Changing the default
   would move certificates already issued, so it needs your word.
