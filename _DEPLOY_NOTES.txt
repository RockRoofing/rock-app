THE ANSWER: IT IS THE FILE, NOT THE USER
==========================================
Their RAMS is bigger than about 4.5MB. Yours is not.

RAMS uploads posted the file's bytes through /api/upload-file - one of our own
serverless functions. Vercel caps a serverless request body at roughly 4.5MB, and
over that the PLATFORM rejects the request before any of our code runs.

That rejection comes back as a PLAIN TEXT body reading "Request Entity Too Large".
The page then called res.json() on it, which is where

    Unexpected token 'R', "Request En"... is not valid JSON

comes from. The "R" is the R of "Request". The message is a JSON parse error
standing in for "that file is too big", which is why it told you nothing.

Nothing to do with permissions, the browser or the project. Two people on the same
screen get different results purely on file size - and a RAMS is a PDF, so it does
not compress on the way up the way a photo does.


THE FIX
========
lib/uploadFile.js - one helper, using @vercel/blob/client, which sends the file
straight from the browser to Blob storage with only a token passing through us. No
serverless body limit. The token endpoint already allows PDFs and up to 200MB.

The design pages have used this route all along. Everything else used the capped
one, which is why Tech Subs and drawing sets upload fine and a RAMS does not.

Switched in this package - the paths that carry DOCUMENTS rather than photos:

    RAMS                                    pages/operations/projects.js
    Project files (all categories)          components/ProjectFiles.js
    Handover scope drawings / documents     pages/handover/form.js
    Procurement & risk row attachments      components/RowAttachments.js

And the error now says what is wrong: "X.pdf is too large to upload. Split it or
compress it and try again." The handover and row attachments were swallowing upload
failures to the console entirely - a scope drawing that never uploaded, with nothing
on screen to say so, is a handover that goes out short.
