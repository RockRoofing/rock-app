These two files are the SAME two files that pkg539 changed, and they contain the

pkg540 (CRM copy buttons) touches a different file and is unaffected.


WHAT WAS WRONG
--------------
Two faults stacked on top of each other, which is why some rows were right and
some were wrong.

FAULT 1 - dashboard.js was reading the wrong field.

  qsName: settings.qsName || ''

settings.qsName is a legacy flat field that almost nothing writes any more. Edit
Project Details writes to peopleOverride.quantitySurveyor and falls back to the
IHM, resolved through resolveProjectPeople(). So on nearly every project qsName
came back BLANK.

This is the third time this exact fault has been found. contractsManager was
fixed, then estimator was fixed, and the comment on the estimator fix even says
"same fix as contractsManager above, which was done and this was not". QS was
sitting directly underneath and was missed both times.

FAULT 2 - retention.js filled the blank with the wrong person.

  qsName: p.qsName || p.estimator || ''

So a blank QS silently became the ESTIMATOR - and on screen that is
indistinguishable from a correct QS. The handful of projects that still have a
legacy settings.qsName came through correctly. Everything else showed the
estimator. Hence some right, some wrong.


THE FIX
-------
dashboard.js   qsName now resolves the same way Edit Project Details does:
               peopleOverride.quantitySurveyor -> IHM -> legacy settings.qsName.

               qsEmail follows the NAME. Falling back to settings.qsEmail while
               the resolver supplies a different name would have paired the
               displayed person with somebody else's address, so the legacy
               email is only used when the resolver has nobody at all.

               New cache marker qsResolved, so existing 4-hour snapshots rebuild
               once instead of quietly serving the old estimator values. Without
               a new marker this fix would sit in the code doing nothing.

retention.js   Estimator fallback removed. Blank now means blank - nobody has
               set a QS on that project, and it can be fixed on Edit Project
               Details. Blank is honest; a wrong name is not.

               There were TWO copies of that fallback in the file (line 293, the
               add-a-project list, and line 318, the main list). Both fixed. The
               column tooltip said "falls back to Estimator" and now does not.


AFTER DEPLOYING
---------------
Expect MORE blanks in the QS column, not fewer. That is the point - those rows
were showing the estimator. Fill them in on Edit Project Details (or the IHM)
and they will come through.

Outstanding Invoices and its PDF read the same dashboard qsName field, so they
pick this up too.


NOT CHANGED - WORTH KNOWING
---------------------------
Two other places still read the legacy flat settings.qsName directly and will
show blank rather than the resolved QS:

  pages/project/[id].js line 606   the team summary block on the project page
  pages/api/project/[id]/report.js line 107   the QS row on the project report

Same class of fault, different screens, and they show nothing rather than the
wrong person - so I have left them alone. Say the word and they follow.
