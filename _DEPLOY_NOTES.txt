1. THE OVERHEADS - AND WHY IT TOOK FOUR ATTEMPTS
--------------------------------------------------
You asked several times and I fixed the wrong thing three times: the call site,
then the actual-months list, then the account seeding. All were real, none was
this.

    config:overhead-hidden-rows

The BUDGETS page totals visibleAccounts ONLY - your screenshot says "28 accounts
hidden", and its TOTAL row excludes them. The cash flow summed every overhead
code including all 28.

Two pages counting different sets of accounts can never agree, and that is exactly
the signature: a FIXED gap within each pair of months - 11,408 in Aug and Sept,
951 in Oct and Nov - because the hidden SET is fixed while the forecast method
changes between the pairs.

I should have diffed the two call sites' inputs the first time you raised it
rather than guessing at candidates. That is what found it in the end, in about ten
minutes.


2. NOVEMBER SALES: 155k vs 194k
--------------------------------
    const salesValue = (net, ret) => { const d = 1 - num(ret) / 100; ... }

retentionPct is a PERCENTAGE on some forecasts and a FRACTION on others. Divide
0.05 by 100 and you get 0.0005 - so a 5% retention grossed up by nothing at all,
and the row read below the P&L on every project stored that way.

    retentionPct 5     divisor 0.9500   correct before and after
    retentionPct 0.05  divisor 0.9995 -> 0.9500

The same dual-format trap the P&L already handles. The band row is labelled "inc.
Retention - matches P&L sales" and now actually does.

CAVEAT: this closes most of the 39k, not necessarily all. The two pages also date
differently - the project page uses each line's appDate, the P&L uses the spread
grid's month - so a period straddling a month end can still differ. If November is
still out by a few thousand after this, that is why, and it is not worth chasing.
