THE HOLE
--------
The session cookie carried NO CUSTOMER and was signed with one global secret:

    { id, email, role, name, exp }

So once TENANCY_ENABLED is on:

  1. sign in at app.rockroofing.co.uk, get a cookie
  2. send that same cookie to wilson.constructionliberation.com
  3. the signature verifies - same secret
  4. requireRole reads role: 'admin' - passes
  5. getClient() resolves Wilson from the host and opens WILSON'S database
  6. Wilson's financials render, to an authenticated Rock session

No forgery. No stolen password. Changing the hostname is the entire attack.

And every guardrail built so far behaves CORRECTLY throughout - the tenant
resolved right, the self-check passed, the database was the correct one. Data
access was tenant-scoped. AUTHENTICATION never was. Closing this was the gap
between "the walls are up" and "the front door is locked".

Demonstrated, old code and new side by side:

  OLD  Rock cookie at wilson's address
       verified as james@rockroofing.co.uk role=admin        BYPASS

  NEW  Rock cookie at rock's address                         allowed   ok
       Rock cookie at wilson's address                       rejected  ok
       Rock cookie at the platform address                   rejected  ok
       platform cookie at rock's address                     rejected  ok
       session issued before this existed, tenancy on        rejected  ok
       single tenant today, no customer resolved             allowed   ok


THE FIX
-------
The session payload gains `t`, the customer it was issued for. withTenant checks
it against the customer resolved from the address, in ONE place covering all 169
wrapped routes.

Only enforced where a session is actually present, so the login page and the
signed public links are unaffected.

Middleware is NOT the place for this - it runs at the edge and cannot reach the
registry to learn which customer a hostname belongs to. It keeps doing what it
does: signature and expiry only.


THE PLATFORM ADDRESS - your point about your own admin domain
-------------------------------------------------------------
Built in now rather than retrofitted, because it changes the session format and
doing it later would mean a second forced sign-out.

  PLATFORM_HOSTS        comma-separated. Your own administration address, e.g.
                        admin.constructionliberation.com. Unset today, so
                        nothing changes.

That address belongs to no customer, so it must not 404 on resolution - and a
session issued there carries the reserved id '~platform', so it cannot be used
against any customer's site, and no customer's session can be used against it.
Both directions proven above.

The platform ADMIN PAGES do not exist yet. This is the door and the lock; the
room comes later.


THE TWO SIGNED PUBLIC LINKS
---------------------------
Variation instruction and In Query review had the same flaw for the same reason:
one signing secret across every customer, so a link issued by one verified on
another's site and then looked its project id up in the wrong database.

Both now carry the customer and check it.

RAMS approval links were ALREADY SAFE and are untouched - those tokens are
stored in the database rather than signed, so a lookup goes through getClient()
and simply cannot find another customer's token.

--------------------------------------------------

Neither happens today. Both happen the moment TENANCY_ENABLED=1 lands.
