WHY CRONS CANNOT USE withTenant
-------------------------------
withTenant works out the customer from the web address the request came to. A
cron has no meaningful address - Vercel calls it on the deployment URL. Wrapping
one would bind it to whichever host it was called on, which in practice means
every cron runs as the first customer forever and never runs for anyone else.
Silently. The sync would stop for everybody except one company and nothing would
say so.

So a cron loops instead:

    export default forEachTenant('wip-sync', handler)


EACH ITERATION IS ISOLATED
--------------------------
One customer's expired Xero token must not stop the job for everyone else. Every
iteration is caught on its own, recorded, and the loop continues. Demonstrated:

    tenant rock    ok
    tenant wilson  FAILED - Xero token expired
    tenant testco  ok
    tenants: 3   succeeded: 2   failed: 1

The response returns 200 even with failures inside, deliberately. The JOB ran.
Returning 500 because one customer out of forty failed would make Vercel report
the whole cron as broken and hide the thirty-nine that worked.


THE RESPONSE PROBLEM, and why it was the risky part
---------------------------------------------------
Every cron handler calls res.json() itself. In a loop that would try to send the
response once per customer, and every call after the first throws "headers
already sent" - which would break all 21 crons at once.

So each iteration gets a CAPTURING response that records what the handler tried
to send, and one combined response goes out at the end.

Tested against the three response shapes that actually occur in these files:
  res.json({...})                       captured, ok
  res.status(401).json({ error: ... })  captured, recorded as a failure with the
                                        handler's own message
  a thrown exception                    caught, recorded, loop continues


HEARTBEATS - the one part that is LIVE TODAY
--------------------------------------------
Every run now records cron:last:<name> in the database: when it started, how
long it took, whether it worked, and the error if not. This happens in the
single-tenant path too, so it starts recording immediately rather than when
multi-tenancy lands.

Nothing reads these yet. The monitoring page you asked about comes later. But a
job that has never recorded anything is the only way to spot one that has
silently stopped, and the recording has to start before it can be useful.

You can read one by hand now if you want to confirm it is working - the value is
at key cron:last:hs-expiry-email and similar.

Writing a heartbeat can never fail the job it is watching - that write is caught
and discarded on error.

A LIMIT WORTH KNOWING NOW
-------------------------
This loop is sequential. A cron taking 30 seconds for one customer takes 30
times N for N customers, against a Vercel function timeout. It is fine for one
customer and fine for a handful. Somewhere around twenty to thirty it stops
fitting, and the crons will need to fan out - one invocation per customer,
queued, rather than one invocation doing everyone.

Not a problem to solve today. But it is a real ceiling and it arrives before a
hundred customers do, so it should not come as a surprise later.
