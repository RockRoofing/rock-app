WHAT EACH FILE IS
-----------------
lib/tenantContext.js
  Request-scoped storage. Answers "which customer is this request for" from
  anywhere in the call stack, however deep, without passing anything down.

lib/tenants.js
  The registry. Reads the control database, caches for 60 seconds, resolves a
  web address to a customer. Two rules built in: a failure is never cached, and
  a stale copy is served if the control database cannot be reached.

lib/withTenant.js
  The wrapper. One line at the top of each API route. Resolves the customer from
  the address and runs the handler with it in scope.

lib/db.js
  getClient() now checks whether a customer is in scope. If one is, it connects
  to THAT customer's database and runs the self-check. If none is, it behaves
  exactly as before.

pages/api/admin/tenant-setup.js
  Admin-only, called by hand. Reports what is configured, writes the identity
  label into a database, registers a customer in the control database. Not
  linked from any page.


THE SELF-CHECK, which is the part worth reading
-----------------------------------------------
The registry says "Wilson is at database X". Database X carries a record at
tenant:identity saying it is Wilson. Before serving anything, the two have to
agree. They disagree - it refuses, loudly.

This does not grant access. It refuses it. It catches a wrong entry in the
registry, which is otherwise the one completely silent failure in the whole
design: everything works, nothing errors, and one company sees another's
projects.

It cannot catch both sides being wrong the same way - a database cloned from
another customer with the label edited to match. Which is why test customers
must be created EMPTY and never cloned. That is a rule for us, not something
the code can enforce.


WHY REQUEST-SCOPED STORAGE AND NOT A VARIABLE
---------------------------------------------
A plain module-level variable holding "the current tenant" looks identical in
the editor and is the most dangerous way to build this. Two requests running at
once in the same warm function would overwrite each other.

Demonstrated, same machine, same moment:

  With request-scoped storage
    slow request (rock) started first   -> rock      OK
    fast request (wilson) started after -> wilson    OK

  With a module variable
    slow request (rock) started first   -> wilson    LEAKED
    fast request (wilson) started after -> wilson    OK

The first request finished by reading the second customer's id. That is one
company's data served under another company's session, and it is invisible in
testing because it only happens under concurrent load.
