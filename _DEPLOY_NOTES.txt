WHAT THE J228 ROW WAS TELLING US
=================================
Two figures on that row cannot both be true:

    MCD   29,405.50   at 0.00% (default)

A zero rate must produce zero. And:

    169,679.70  -  140,274.20  =  29,405.50

exactly. So the "MCD" was not a discount at all. It was the gap between two
different sources being subtracted from each other.


FAULT 1 - THE GROSS CAME FROM THE STAMP, THE NET FROM THE APPLICATION
-----------------------------------------------------------------------
pkg800 took Gross AFA from the figure stamped at send. But Final Account was still
being taken from sentSum.finalSubTotal - recomputed from the stored application -
with no check that the two belonged together. mcdValue is computed as
afaBeforeMcd - afa, so the whole difference between the two sources was reported as
Main Contractor's Discount, on a project set to 0%.

Gross and net are now only paired when the gross IS that summary's own anticipated
final account. Otherwise the Final Account is derived from the same gross using the
MCD placement flags, and the row always satisfies gross - MCD = Final Account.


FAULT 2 - THE STAMP WAS STALE, AND I PREFERRED IT
---------------------------------------------------
Your application 2 reads 140,274.20. The stamp said 169,679.70 - out by 29,405.50.

The stamp is only rewritten on SEND, so editing a sent application without
re-sending leaves the old figure behind. pkg800 preferred it, which was the wrong
call: the stored application IS the application, and recomputing from it gives what
the applications page shows.

Order of preference is now:

  1. the latest sent application, as it stands now
  2. the figure stamped at send      - only where 1 cannot be computed
  3. a stored override               - only where there is no sent application
  4. project details

Verified on your J228 figures:

    Gross AFA        140,274.20   application 2 (sent)
    MCD                    0.00   <- was 29,405.50 at 0%
    Final Account    140,274.20
    gross - MCD = Final Account    true
    stamp flagged stale            true


FAULT 3 - THE ROW NOTE CONTRADICTED ITSELF
--------------------------------------------
"stale override saved" was showing next to "application 2 (sent, as issued)" -
saying in one breath that the stamp was in use and that it was stale. The flag was
`hasOverride && afaFromApplication != null`, which is true on every row that has
ever had an application sent.

Two separate notes now, and neither fires on a healthy row:

  "edited since sent"   the application was changed after it was sent, so the saved
                        figure and the live one differ. Re-send to bring them back
                        into line. THIS is what J228 will show.

  "older figure saved"  a figure left by an EARLIER application is still stored but
                        is not being used.
