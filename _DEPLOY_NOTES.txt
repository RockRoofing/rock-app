WHAT IS THERE NOW
==================
CATEGORISED BY DEFAULT. Every row on this tab is tagged - to the In Query option -
so the page's usual "No category assigned" default showed an empty tab. It switches
on arrival and switches back when you leave, so the other tabs keep their default.

GROUPED BY INVOICE, with a chevron to open the lines, the same as the Costs tab on a
project. Four lines on one Renolit invoice are one row at the invoice total, not
four rows to answer separately.

SORTABLE. Click any header. Click again to reverse.

USER RESPONSIBLE. A dropdown of portal users, plus "Someone else..." for a name
typed in. A typed name MUST have an email address - the list is sent to them and the
link they get is tied to it, so a name with no address could never be told.

STATUS. In Query or Approved. Everything starts In Query: the absence of a decision
is not approval, so an invoice nobody has touched still counts as outstanding.

COMMENTS. A thread per invoice, from both sides, with the latest shown on the row.

FILTERS. By status - In Query / Approved / Both, defaulting to In Query - and by
person, listing only the names actually on the table rather than the whole staff
list.

SEND LIST. Emails what is on screen, grouped so somebody with nine queries gets one
email with nine lines rather than nine emails. Already-approved items are not
re-sent. Afterwards it reports one line per recipient, because "sent" on its own
cannot tell you which of five people did not get it.


THE REVIEW LINK
================
The email contains a link to /inquery-review. It is NOT behind the portal login, and
middleware.js is changed to allow it and its API through - the people answering
these are often not portal users, and without those two lines the link bounces to a
login page they cannot get past.

The signed token IS the authentication. It names one email address, it expires after
60 days, and it SCOPES the response: a token only ever returns the invoices assigned
to that address, so a forwarded link cannot show somebody else's queries.

On that page they see each invoice, its lines and its total, and can Approve, put it
back In Query, or add a comment. Marking it either way is written into the thread as
a note, so it reads as a history rather than a status that silently changed.

The page never reads Xero. It shows a snapshot of the lines taken when the list was
sent, which is why the send writes that snapshot onto the record.


APPROVED IS NOT THE END OF IT
===============================
Approving records that the cost is right. It does not move the cost.

The bookkeeper then re-tags it in Xero from In Query to the project, at which point
it stops arriving as In Query and disappears from the tab on its own - it needs no
action here and nothing is deleted. The record stays, so the Approved filter still
shows what was said about it right up until it is re-tagged.


TWO THINGS WORTH KNOWING
=========================
KEYED BY date|supplier|reference, matching how the Costs tab groups. The bookkeeping
feed carries no Xero invoice id, so there is nothing more stable to use. If a
supplier's date or reference is edited in Xero, that invoice reads as a new one and
its comments stay with the old key.

STILL OUTSTANDING FROM pkg827: In Query is a tracking option, so it will also be
showing up as a PROJECT on Project Financials and the dashboard, with costs and no
revenue. This package does not change that. It wants deciding alongside whether
there are other non-project options - Suspense, Overheads - doing the same job.
