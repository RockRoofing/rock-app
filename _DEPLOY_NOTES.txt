ROOT CAUSE - MY MISTAKE
------------------------
The good news is the plumbing is now working: the request reached the API and the API
answered. It just refused you, wrongly.

getOpsProjects() returns the RAW project records, where the fields sit NESTED under .data:

    { projectNo: 'J203', data: { contractsManager: 'Will Smith', ... } }

I read x.contractsManager off that record. On a raw record that is ALWAYS undefined - the
CM lives at x.data.contractsManager. It is /api/ops-projects that flattens the records,
and that is what the Site App itself calls, which is exactly why the project appears in
your list (flattened, CM found) and then refuses to open (raw, CM undefined).

So the check was comparing your name against an empty string for every project, and
nameMatches() returns false when either side is blank. It would have refused EVERY project
for EVERY user - it was never going to let anyone in.

That is the same nested-vs-flattened trap as the dashboard:cache array bug earlier in this
run. I should have checked the shape rather than assuming.


THE FIX
-------
Reads x.data.contractsManager, falling back to x.contractsManager, so it works whichever
shape it is handed.

Two other improvements while in there:

1. A commercial OVERRIDE of the CM now also grants access. If Edit Project Details shows
   you as CM because of an override, the Site App agrees - previously only the Ops value
   counted, so an overridden CM would have been locked out even after the fix above.

2. If it ever does refuse, the message now names the project and says who the CM actually
   is - e.g. "You are not listed as the Contracts Manager on J203. It is currently set to
   Will Smith." - instead of a flat denial with nothing to act on.
