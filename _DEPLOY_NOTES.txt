WHAT IT SEARCHED BEFORE
------------------------
Title, organization, contact person. Three fields.

WHAT IT SEARCHES NOW
---------------------
Those three plus every field on the Details card:

  Glenigan ID, site location, region, size m2, credit score, credit limit,
  insured credit limit, project stage, roofing works onsite, estimator
  responsible, scope of works, general info, sales person, project start date,
  project type, lead source

Scope of works and general info are the useful ones - free text, and usually
where somebody has written the thing you are trying to find. Searching
"tapered", "mansafe" or a postcode now returns the project.

Applies to Kanban, List and Activities. All three read one function.

HOW IT IS BUILT
---------------
DETAIL_KEYS lived inside the deal editor component, so the filters could not see
it. It is now CRM_DETAIL_KEYS at module scope, with a dealHaystack(deal) helper
beside it, and the editor reads the same constant.

Two copies of that list would drift, and a search that quietly stopped covering
a field is a fault nobody reports - you just assume the project is not there.

Activity rows carry the haystack from the deal they were built from, computed
once with the row rather than rebuilt on every keystroke.

Both are declared at the top of the file, above every use. A const read before
its declaration throws at runtime and compiles cleanly, which has taken this
file out before.
