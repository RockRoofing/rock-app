pkg426 - clicking one project opened another. Duplicate ids.
============================================================

Deploy after pkg425. This one matters - deploy it before creating any more projects.

CHANGED FILES (replace)
-----------------------
  pages/crm.js
  pages/crm-scores.js
  pages/api/crm.js

NEW FILES: none.


THE CAUSE
---------
New projects took their id from a counter that was hard-coded:

    const nextId = useRef(900000)

Nothing ever moved it off 900000. It is a REF, so it resets every time the page loads.
Create a project today and another tomorrow and BOTH get id 900000.

The CRM opens a deal with  deals.find(d => d.id === openId)  - which returns the FIRST
match. So clicking the newer project opened the older one. Exactly what you saw.

Reproduced on the bench: two projects both on 900000, clicking the second returns the
first.

It would also have affected saving, filed email, activities - anything keyed by deal id.
Two projects sharing an id share everything hung off it.


FIXED, TWO PARTS
----------------
1. NO MORE COLLISIONS. The counter is now seeded above the highest id actually present,
   and re-seeded whenever the deal list changes - so a project someone else created
   between loads cannot be collided with either.

2. THE ONES ALREADY BROKEN. Go to /crm-scores - there is a red panel at the top.

       "Check for duplicates"   lists them, changes nothing
       "Renumber n"             fixes them, after a confirmation

   The FIRST project with each id KEEPS it - it is the one already referenced by
   activities, notes, filed email and planning allocations. Later ones are renumbered
   above the highest id in use, and their activities and notes are copied across with
   them.

   Check first. It tells you exactly which projects are hidden behind which.


ONE THING THE RENUMBER CANNOT MOVE
------------------------------------
Filed email (crm:emails:<id>) and planning allocations (N:<dealId>) still point at the
ORIGINAL id. For a renumbered project those now belong to the project that kept the id.

In practice this is unlikely to bite - the affected projects are ones created in the last
few days, and they will not have email filed against them or labour allocated yet. But if
a renumbered project looks like it has somebody else's email on it, that is why, and the
Move button on the Email section will put it right.
