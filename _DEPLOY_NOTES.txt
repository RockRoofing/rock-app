1. APPLIED FOR NOT MATCHING ON SOME ROWS - FOUND
------------------------------------------------
dashboard.js had two different applications feeding the two columns:

    const latest = apps[apps.length - 1]              <- ANY status
    appliedForLatest = sum.current.netBeforeRet       <- from `latest`

    const latestSent = sentApps[sentApps.length - 1]  <- SENT only
    certifiedGross  = sentSum.previously.gross        <- from `latestSent`

So Applied for read the latest application of any status. A draft somebody had
started but never issued silently superseded the sent one, and the tracker showed a
figure that appears on no certificate.

That is why it looked intermittent: it only goes wrong on projects where a draft
exists. Everywhere else `latest` and `latestSent` are the same application.

The column tooltip has promised "the sent application wins" since pkg792. The code
never did it. Both columns now read the latest SENT application.

Also hoisted: previously-certified was computed by two different rules in the same
file. There is now one prevGrossFor() and both consumers use it - prevCertGross
first, the preceding application's grossCurrent only where it is absent.


2. CERTIFIED NOT PULLING THROUGH - LIKELY A DEFINITION, NOT A BUG
------------------------------------------------------------------
Certified is sourced from PREVIOUSLY CERTIFIED on the latest sent application -
what the customer certified BEFORE that application. On a project whose only sent
application is App 1 that is legitimately zero, so the column reads blank. It will
also read blank wherever prevCertGross was never typed and there is no earlier
application to recompute from.

I have not changed the meaning, because there are two defensible ones and picking
the wrong one silently is worse than asking. Both figures are now carried and shown
side by side in the new drill-down:

  Certified (shown)              = previously certified, EXCLUDES the latest app
  Gross on the sent application  = cumulative gross, INCLUDES the latest app

Open the drill-down on a row where Certified is blank and tell me which of those
two is the number you want. It is a one-line change once decided.


3. NEW: APPLIED FOR / CERTIFIED DRILL-DOWN
-------------------------------------------
Click the Applied for cell on any row. Same shape as the 612 drill-down: it shows
how many applications exist and how many are sent, which application each column
read, its status, and every candidate figure - so a wrong number can be read rather
than guessed at. Always on, whether or not anything looks wrong.

Three banners fire on their own conditions:
  - a later DRAFT exists, with what it would have shown before this package
  - no SENT application at all, so both columns fall back to typed values
  - Certified blank because nothing was certified before the first application


4. CERTIFIED NOW EDITABLE INLINE
---------------------------------
Click the value in the cell. Enter or clicking away saves, Escape cancels.

Built as a MODULE-SCOPE component. A component declared inside another component is
a new type on every render, so React remounts the subtree - the classic "input loses
focus after one keystroke" bug. It saves through the existing saveEntry path, so a
Xero-derived row still becomes a manual override in the normal way. The diagnostic
blob is stripped before saving so it does not get written into Redis.

Still true, and by design: the next application sent overwrites a typed value.
