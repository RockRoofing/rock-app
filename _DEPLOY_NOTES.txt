pkg297 - H&S Matrix: columns can actually be deleted
=====================================================

REPLACES pkg295 and pkg296 - it carries the frozen header row and the click-to-sort
headers as well. Deploy this one and skip those.

CHANGED FILES
-------------
  pages/api/hs-matrix.js               THE FIX
  pages/operations/hs/hs-matrix.js     frozen header + sorting (from pkg295/296)

No new files. Both straight replacements.


ROOT CAUSE
----------
The delete itself was working perfectly. Something else was putting the column back.

pages/api/hs-matrix.js holds a list of ~36 DEFAULT_COLS - the standard training columns.
Every single read of the matrix ran ensureColumns(), which backfills any default column
that is not currently present, matching on label:

    for (const label of DEFAULT_COLS) {
      if (!have.has(label.toLowerCase().trim())) { cols.push({ id: ...new id..., label }) }
    }

So deleting a built-in column removed it correctly - and then the very next load found it
"missing" and re-created it with a brand new id, pushed onto the END of the list. Exactly
the behaviour you described: it moves to the end and will not go away.

That backfill exists for a good reason - it is how new standard columns reach an existing
matrix without anyone re-adding them by hand. The problem was that it could not tell
"never had this one" from "deliberately got rid of this one".

Columns YOU added were always deletable - they are not in DEFAULT_COLS, so nothing put
them back. Only the built-in ones were stuck.


THE FIX
-------
A deleted default column's label is now recorded in a new store,
ops:hs-matrix-removed-defaults, and the backfill skips anything on that list. So:

  - deleting a built-in column now sticks, permanently
  - genuinely new default columns added in a future release still appear automatically
  - re-adding a column with the same name clears it from the list, so the two can never
    disagree about whether it should exist

Deleting still removes all the dates held against that column, as it always did, and is
still blocked on locked columns.
