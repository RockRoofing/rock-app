WHAT I BROKE
------------
pkg861 added this to lib/variationInstruct.js and lib/inquery.js:

    import { currentTenantId } from './tenantContext'

tenantContext.js imports async_hooks, which is a Node module with no browser
equivalent.

lib/variationInstruct.js is imported by TEN client-side files - wip.js,
variations.js, applications.js, contracted-rates.js, VariationBuilder.js,
ProjectDatesModal.js and others - for projectVariations() and projectLabel().
lib/inquery.js is imported by components/InQueryTable.js.

So async_hooks was dragged into the browser bundle, webpack could not resolve
it, and every build from that commit onwards failed.


WHY MY CHECKS MISSED IT
-----------------------
esbuild compiles each file ON ITS OWN. It never walks the import graph, so it
cannot see that a server-only module is reachable from a page. Every one of the
files I changed compiled cleanly in isolation, which is exactly what I reported,
and the report was true and useless.

This is a class of fault my checks had no coverage for at all.


THE FIX
-------
The tenant is now PASSED IN to the four token functions rather than read from
request-scoped storage inside them. Only server-side callers know the tenant, so
only they pass it:

  createInstructToken({ ..., tenantId })     verifyInstructToken(token, tenantId)
  createReviewToken({ ..., tenantId })       verifyReviewToken(token, tenantId)

Five callers updated: variation-send.js, cron/variation-reminders.js,
variation-instruct.js, bookkeeping-inquery.js, inquery-review.js. All server
side, all already wrapped, so currentTenantId() is available in each.

The behaviour is identical to what pkg861 intended. Only where the tenant is
read from has changed.

Both library files now carry a comment saying why the import is not there, so
the next person to "tidy it up" does not put it back.


THE NEW CHECK
-------------
I have added an import-graph walk to my own checks: start at every client-side
entry point - 185 pages and components - follow every relative import, and flag
any that reaches a server-only module.

  before the fix:  lib/tenantContext.js imports async_hooks,
                   reached from 10 client files
  after the fix:   CLEAN

I verified it by putting the bad import back temporarily and confirming it fires,
then removing it again. A check nobody has seen fail is not a check.

One deliberate omission: 'crypto' is not on the server-only list, even though
variationInstruct.js imports it from client-reachable code. Deployment 860 built
cleanly with that in place, so Next resolves it for the browser. Listing it would
produce a permanent false positive, and a check people learn to ignore is worse
than no check at all.
