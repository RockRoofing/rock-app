pkg792 - J147 612: a dead-end allocation was suppressing the reference fallback

FILES (both already exist - overwrite in place, no new files)
  pages/api/dashboard.js
  pages/retention.js

WHAT WAS WRONG
  The App 2 credit note carries ONE Xero allocation. That allocation resolves to a
  document that cannot be the reversal - its 612 line is the same way up as the credit
  note's. The pairing code was written as:

      const byRef = byAlloc.length ? [] : (...)

  so as soon as the allocation resolved to ANYTHING, the reference fallback was switched
  off - even though the allocation candidate was then rejected two lines later. The pair
  was never cancelled and both columns stayed inflated by 642.20.

  This is why pkg790's fallback appeared not to work: it was correct, and it never ran.

WHAT CHANGED
  1. Allocation matching and reference matching BOTH always run. Allocation is still
     tried first; reference is the fallback, deduped against it.
  2. One key function (lineKey) for a document everywhere. The cancel set keyed on
     `xeroInvoiceId || invoiceNumber`, the offset map on `String(xeroInvoiceId)` alone -
     where an id is null those collide as 'null' across unrelated lines.
  3. New MATCH column in the 612 drill-down showing how each credit note paired, or why
     it did not. Always on, whether or not anything is wrong.
  4. Cache marker bumped to ret612Match_v1 - the old cache will not be served.

STILL WORTH KNOWING (not a bug in the app)
  The Feb-2024 App 2 invoice holds a POSITIVE 612 line in Xero (+642.20). A deduction
  should be negative. So Xero itself recorded App 2's retention the wrong way up, which
  is almost certainly why it was credited out and re-raised in Nov 2025 at -33.80. The
  app now nets it away correctly either way, but the original entry is still wrong in
  Xero if you want the account itself to read properly.
