YOUR QUESTION: IS IT BECAUSE THE PROJECT WAS ADDED VIA EDIT PROJECT DETAILS?
=============================================================================
Close, but the mechanism is not "how it was added" - it is that the two figures are
built from two entirely separate sets of numbers, and nothing keeps them in step.

    Gross AFA (application)  = measuredContractSum + variationsFinal
                               BOTH taken from the APPLICATION - its own contract
                               works schedule, and its own variations list, FROZEN
                               at the moment it was sent (applications.js line 344)

    Final account (project)  = contractValue + instructed variations
                               from Edit Project Details

They agree only if the schedule on the application adds up to the contract value AND
no variation has been instructed since the last application went out.

So on a project set up in Edit Project Details first, the application's contract
works schedule was typed separately. If it was only partly populated - the items
being claimed rather than the whole contract - measuredContractSum comes in below
contractValue and Gross AFA reads low. The application always wins, so that is the
figure you see.

The other common cause is a variation instructed AFTER the last application was
sent. It is in project details and not in the frozen application, so Gross AFA is
behind by exactly that variation.

Rather than tell you which one it is on your project, the drill-down now shows it.


1. NEW: GROSS AFA DECOMPOSITION IN THE DRILL-DOWN
--------------------------------------------------
Click the Applied for cell on the row that is wrong. A second table now shows both
sides of the sum:

    Measured contract sum (app)          the schedule ON the application
    Variations at final value (app)      with instructed / total counts
    = Gross AFA from the application

    Contract value (project details)
    Instructed variations (project)      with instructed / total counts
    = Gross AFA from project details
    Stored override

Where the two disagree by more than a pound, a banner says by how much and
attributes it to whichever component accounts for most of the gap - the measured
contract sum, or the variations. Verified against both shapes:

    schedule short of contract value  -> blamed on measured contract sum
    variation instructed after send   -> blamed on variations


2. FIXED: SEVEN PLACES STILL USED THE OLD INSTRUCTED TEST
-----------------------------------------------------------
This can also make the project-details side wrong on its own.

pkg766 established isInstructed() as the single rule, because the field is a boolean
on records written by the current UI and the STRING 'yes'/'no' on older ones:

    v.instructed !== false   counts a MISSING flag as instructed
    !!v.instructed           counts the STRING 'no' as instructed

pkg766 fixed applicationPdf.js and applications.js. It did not fix the dashboard or
the project page, which between them had seven copies of `filter(v => v.instructed)`
- the second form. So a variation recorded as 'no' on an older project was counted
as instructed in:

    dashboard.js   project-details AFA, labour budget, materials budget
    project/[id].js  AFA, labour budget, materials budget, the edit-form preview

All seven now call isInstructed(). If your mismatched project is an older one with
variations marked 'no', this alone may close the gap - and the drill-down will show
it, because the instructed/total counts are on both lines.

Also hoisted contractValue and instructedVars above the applications block so the
diagnostic decomposes against the same figures the column uses, rather than a second
copy of the rule.


WORTH KNOWING - not changed
----------------------------
anticipatedFinalAccount is measuredContractSum + variationsFinal. It does NOT
include materialsFinal. Materials on site are a temporary claim rather than account
value, so excluding them is right - but if your gap is exactly the materials figure,
that is why.
